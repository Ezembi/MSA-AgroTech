## Ссылка на базовое решение

Данный ADR основан на архитектурном решении **«Толстый клиент»** (полноценный бэкенд на каждой ферме), как единственный способ обеспечить:
- отказоустойчивость 99,95% при нестабильном интернете;
- время реакции на инцидент ≤5 секунд;
- полную автономность фермы при отсутствии связи.

Переход в SaaS **не меняет** архитектуру агента на ферме. Эволюция касается **центральной платформы**: добавляется мультитенантность, биллинг и API для клиентов.

### Варианты изоляции данных

Рассмотрено три варианта изоляции данных между тенантами.

#### Критерии сравнения

| **№** | **Критерий**                     | **Описание**                                                           | **Приоритет** | **Коэффициент** |
|:-----:|:---------------------------------|:-----------------------------------------------------------------------|:-------------:|:---------------:|
|   1   | Изоляция данных                  | Степень независимости данных одного тенанта от другого                 |   Критичный   |        3        |
|   2   | Стоимость инфраструктуры         | Операционные затраты на поддержку N тенантов                           |    Высокий    |        2        |
|   3   | Масштабируемость                 | Лёгкость добавления нового тенанта и рост числа ферм                   |    Высокий    |        2        |
|   4   | Сложность инициализации          | Время и сложность подключения нового клиента                           |    Высокий    |        2        |
|   5   | Соответствие требованиям 152-ФЗ  | Возможность размещения данных клиента в отдельном физическом хранилище |    Средний    |        1        |
|   6   | Сложность резервного копирования | Удобство изолированных бэкапов и восстановления на уровне тенанта      |    Средний    |        1        |

#### Вариант 1: Изоляция на уровне схем БД (Shared Database, Separate Schemas)
**Диаграмма:** [C2_variant1_schema.puml](C2_variant1_schema.puml)

Один инстанс PostgreSQL содержит отдельную схему (`schema_tenant_X`) для каждого клиента. Tenant Resolver при каждом запросе устанавливает `SET search_path = schema_tenant_X`.

| **№** | **Критерий**             | **Оценка × К-т** | **Обоснование**                                                                                                            |
|:-----:|:-------------------------|:----------------:|:---------------------------------------------------------------------------------------------------------------------------|
|   1   | Изоляция данных          |  3 × 3 = **9**   | Логическая изоляция. Ошибка в коде или migration может затронуть другие схемы. Row-level security требует явной настройки. |
|   2   | Стоимость инфраструктуры |  5 × 2 = **10**  | Минимальные затраты: один инстанс на всех.                                                                                 |
|   3   | Масштабируемость         |  4 × 2 = **8**   | Хорошо масштабируется по числу тенантов до нескольких сотен, но общий инстанс становится узким местом.                     |
|   4   | Сложность инициализации  |  5 × 2 = **10**  | Подключение = CREATE SCHEMA + Flyway migration. Очень быстро.                                                              |
|   5   | Соответствие 152-ФЗ      |  2 × 1 = **2**   | Сложно гарантировать физическую изолированность хранилища для отдельного клиента.                                          |
|   6   | Резервное копирование    |  3 × 1 = **3**   | Pg_dump на уровне схемы возможен, но сложнее в восстановлении под нагрузкой.                                               |
|       | **Итого**                |    **42/57**     |                                                                                                                            |

**Компромисс:** низкая стоимость, но слабая физическая изоляция и риск «шумного соседа».

---

#### Вариант 2: Изоляция на уровне отдельных БД (Shared Instance, Separate Databases)
**Диаграмма:** [C2_variant2_db.puml](C2_variant2_db.puml)

Один инстанс PostgreSQL содержит отдельную базу данных (`db_tenant_X`) для каждого клиента. DB Connection Router (PgBouncer + Spring Routing) маршрутизирует соединения на основе `tenant_id` из контекста запроса.

| **№** | **Критерий**             | **Оценка × К-т** | **Обоснование**                                                                                            |
|:-----:|:-------------------------|:----------------:|:-----------------------------------------------------------------------------------------------------------|
|   1   | Изоляция данных          |  4 × 3 = **12**  | Базы данных полностью изолированы: права, транзакции, DDL. Пользователь тенанта не может видеть другую БД. |
|   2   | Стоимость инфраструктуры |  4 × 2 = **8**   | Один инстанс, но накладные расходы выше схемной изоляции из-за отдельных connection pools.                 |
|   3   | Масштабируемость         |  4 × 2 = **8**   | Хорошо масштабируется. При росте — PostgreSQL instance можно вертикально масштабировать.                   |
|   4   | Сложность инициализации  |  4 × 2 = **8**   | CREATE DATABASE + Flyway migration. Несколько сложнее схем, но автоматизируется через Tenant Mgmt Service. |
|   5   | Соответствие 152-ФЗ      |  3 × 1 = **3**   | Данные в отдельной БД, но на общем инстансе. Для строгих требований — недостаточно.                        |
|   6   | Резервное копирование    |  5 × 1 = **5**   | pg_dump per database — просто, стандартно, легко восстанавливать.                                          |
|       | **Итого**                |    **44/57**     |                                                                                                            |

**Компромисс:** баланс между изоляцией, стоимостью и удобством эксплуатации. Оптимальный вариант для большинства клиентов.

---

#### Вариант 3: Изоляция на уровне инстансов (Separate Database Instances per Tenant)
**Диаграмма:** [C2_variant3_instance.puml](C2_variant3_instance.puml)

Каждый тенант получает выделенный инстанс PostgreSQL (отдельный Pod в Kubernetes / отдельная VM). DB Instance Registry хранит маппинг `tenant_id -> connection string` и динамически предоставляет соединение.

| **№** | **Критерий**             | **Оценка × К-т** | **Обоснование**                                                                                       |
|:-----:|:-------------------------|:----------------:|:------------------------------------------------------------------------------------------------------|
|   1   | Изоляция данных          |  5 × 3 = **15**  | Максимальная изоляция: отдельные процессы, файловая система, сеть. Нет «шумного соседа» вообще.       |
|   2   | Стоимость инфраструктуры |  2 × 2 = **4**   | Высокая стоимость: N инстансов PostgreSQL. При 50 тенантах — 50 отдельных под/VM.                     |
|   3   | Масштабируемость         |  3 × 2 = **6**   | Каждый тенант масштабируется независимо, но количество инстансов растёт линейно.                      |
|   4   | Сложность инициализации  |  2 × 2 = **4**   | Требует IaC (Terraform/Helm) для автоматизации. Подключение занимает минуты, но сложнее в поддержке.  |
|   5   | Соответствие 152-ФЗ      |  5 × 1 = **5**   | Данные клиента физически изолированы. Можно размещать на выделенных серверах для compliance-клиентов. |
|   6   | Резервное копирование    |  5 × 1 = **5**   | Независимые бэкапы и RPO/RTO per tenant.                                                              |
|       | **Итого**                |    **39/57**     |                                                                                                       |

**Компромисс:** максимальная изоляция и compliance, но высокая стоимость. Оправдан для Enterprise-клиентов.

---

### Итоговое решение по изоляции данных

**Рекомендация: Вариант 2 (Separate Databases) как основа, с опциональным Вариантом 3 для Enterprise-сегмента.**

| **Тариф**  | **Модель изоляции**                      | **Обоснование**                                                          |
|:-----------|:-----------------------------------------|:-------------------------------------------------------------------------|
| Basic      | Shared Instance, Separate Databases (V2) | Стандартная изоляция по БД. Бюджетный тариф для небольших агрохолдингов. |
| Standard   | Shared Instance, Separate Databases (V2) | Полная изоляция данных при разумных затратах.                            |
| Enterprise | Separate Instances (V3) — опционально    | Для клиентов с требованиями 152-ФЗ или индивидуальным SLA.               |

## Задача 2. Система биллинга и монетизации

### Тарифные планы

| **Тариф**  | **Фермы** | **Камеры/ферма** | **API-вызовов/мес** | **Поддержка** |
|:-----------|:---------:|:----------------:|:-------------------:|:-------------:|
| Basic      |    1–5    |      до 10       |       100 000       |     Email     |
| Standard   |   6–30    |      до 30       |      1 000 000      | Email + Chat  |
| Enterprise |    31+    |   Неограничено   |    Неограничено     |  Выделенный   |

Базовый принцип тарификации — **per farm / per event** (число активных ферм + объём событий в день).

### Архитектура биллинга

**Ключевые сервисы:**
- **Billing Service** — управление жизненным циклом подписки, расчёт стоимости на основе usage-данных (потребляет события из Kafka), генерация счетов и история транзакций.
- **Payment Adapter** — Facade для работы с платёжными системами. Обрабатывает колбэки (webhook-верификация по HMAC), управляет повторными попытками.
- **Core Business Logic** — в том числе сбор usage-метрик из Kafka-событий ферм и запись агрегированных данных в ClickHouse для тарификации.

### Интеграция с российскими платёжными системами

| **Провайдер** | **Тип интеграции**  | **Поддерживаемые методы**                          | **Назначение**                                         |
|:--------------|:--------------------|:---------------------------------------------------|:-------------------------------------------------------|
| ЮKassa        | REST API + Webhooks | Банковская карта, СБП, ЮMoney, корпоративная карта | Основной провайдер, рекуррентные платежи по подписке   |
| CloudPayments | REST API + Webhooks | Банковская карта, СБП, Apple Pay, Google Pay       | Резервный провайдер, fallback при недоступности ЮKassa |

**Схема рекуррентных платежей:**
1. При активации подписки клиент вводит карточные данные через hosted-форму провайдера (токенизация).
2. `Billing Service` в день списания вызывает `Payment Gateway Adapter` с суммой и токеном карты.
3. Адаптер направляет запрос к ЮKassa. При ошибке — retry с экспоненциальной задержкой (3 попытки), затем fallback на CloudPayments.
4. При неуспешном списании — `Notification Service` отправляет Email/SMS клиенту. Подписка переводится в grace-period (7 дней), затем — suspension.

## Задача 3. Интеграции с клиентами

### Public REST API

API предоставляет клиентам доступ к данным их ферм, поголовья и инцидентов. Доступный scope функционала зависит от тарифного плана.

**Базовый URL:** `https://api.agrotech-saas.ru/v1/`

| **Ресурс**                     | **Метод** | **Описание**                                          | **Доступ (тариф)**    |
|:-------------------------------|:---------:|:------------------------------------------------------|:----------------------|
| `/farms`                       |    GET    | Список ферм тенанта                                   | All                   |
| `/farms/{id}/animals`          |    GET    | Поголовье на конкретной ферме                         | All                   |
| `/farms/{id}/incidents`        |    GET    | Инциденты (драки, гибель, задавливание поросят)       | All                   |
| `/farms/{id}/metrics`          |    GET    | Метрики фермы (кормление, поение, температура)        | Standard / Enterprise |
| `/farms/{id}/devices`          |    GET    | Состояние устройств (кормушки, поилки)                | Standard / Enterprise |
| `/farms/{id}/devices/{id}/cmd` |   POST    | Команда управления устройством                        | Standard / Enterprise |
| `/analytics/herd-count`        |    GET    | Динамика поголовья по периоду                         | Enterprise            |
| `/analytics/incidents/summary` |    GET    | Сводка инцидентов по периоду                          | Enterprise            |
| `/webhooks`                    | GET/POST  | Управление webhook-подписками                         | All                   |
| `/billing/subscription`        |    GET    | Информация о текущей подписке                         | All                   |
| `/billing/invoices`            |    GET    | История счетов                                        | All                   |

**Аутентификация:** Bearer-токен (OAuth2 Authorization Code Flow) или API-ключ (для server-to-server интеграций).

**Версионирование:** URI-based (`/v1/`, `/v2/`). Старая версия поддерживается минимум 12 месяцев после выпуска новой.

### Webhook-события

| **Событие**               | **Описание**                                  | **Доступ**            |
|:--------------------------|:----------------------------------------------|:----------------------|
| `incident.created`        | Зафиксирован инцидент (драка, гибель и т.д.)  | All                   |
| `animal.death.confirmed`  | Подтверждена гибель животного                 | All                   |
| `herd.count.updated`      | Обновлён счётчик поголовья                    | Enterprise            |
| `device.alarm`            | Критическая неисправность кормушки / поилки   | Standard / Enterprise |
| `sync.completed`          | Ферма успешно синхронизировалась с платформой | All                   |
| `billing.invoice.created` | Выставлен новый счёт                          | All                   |
| `billing.payment.failed`  | Платёж не прошёл                              | All                   |

### Developer Portal

Реализован на базе **Docusaurus** (документация) + **Swagger UI** (интерактивное API) + встроенный **Sandbox**-тенант для тестирования без реальных данных.

**Содержимое портала:**
- Quickstart-гайд: от регистрации до первого API-вызова за 15 минут.
- Справочник API (OpenAPI 3.0, автогенерация из Spring аннотаций).
- Webhook-документация с примерами payload.
- SDK-примеры (Python, Java, JavaScript/TypeScript).
- Управление API-ключами и webhook-подписками (self-service).
- Changelog и migration-гайды при выходе новых версий API.

## Задача 4. Финальная архитектура To-Be

### C1 — Контекстная диаграмма
**Диаграмма:** [C1_final.puml](C1_final.puml)

Платформа «АгроТехPro SaaS» является центральным узлом экосистемы:
- Клиенты (агрохолдинги) взаимодействуют через Self-Service Portal.
- Разработчики клиентов интегрируют внутренние системы через Public REST API и webhooks.
- Агенты на фермах синхронизируют данные по HTTPS REST (допустимая задержка до 10 минут).
- Биллинг осуществляется через ЮKassa и CloudPayments (российские провайдеры).
- Платформа направляет уведомления через SMS/Email-провайдеров.

### C2 — Финальная контейнерная диаграмма
**Диаграмма:** [C2_final.puml](C2_final.puml)

Платформа включает следующие ключевые контейнеры:

| **Контейнер**             | **Технология**            | **Назначение**                                     |
|:--------------------------|:--------------------------|:---------------------------------------------------|
| API Gateway               | Kong / Nginx              | Rate limiting, routing, SSL termination            |
| Auth Service              | Keycloak                  | OAuth2 / OIDC, realm per tenant, SSO               |
| Tenant Manager            | Java/Spring               | Реестр клиентов, провизионинг БД                   |
| Farm Aggregation Service  | Java/Spring               | Приём sync-данных с ферм, агрегация событий        |
| Core Business Logic       | Java/Spring               | Аналитика поголовья, алерты, метрики               |
| Billing Service           | Java/Spring               | Тарификация, выставление счетов                    |
| Payment Adapter           | Java/Spring               | Интеграция с ЮKassa / CloudPayments                |
| Self-Service Portal       | TypeScript/React          | Личный кабинет: фермы, подписка, отчёты            |
| Developer Portal          | Docusaurus + Swagger UI   | Документация API, sandbox, API-ключи               |
| Message Broker            | Apache Kafka              | Async-обмен: события ферм, биллинг, алерты         |
| Tenant Databases          | PostgreSQL                | Отдельная БД на каждого тенанта                    |
| Metrics Store             | ClickHouse                | Usage-метрики для биллинга и аналитики             |
| Cache                     | Redis                     | Сессии, rate-limit, tenant-конфиг                  |

**Ключевые архитектурные решения:**
- **Изоляция данных:** Вариант 2 (Separate Databases per Tenant) — каждый тенант получает отдельную БД. Enterprise-клиентам предлагается Вариант 3 (отдельный инстанс).
- **Auth:** Keycloak с realm per tenant обеспечивает изоляцию пользователей и ролей.
- **Async обмен:** Apache Kafka развязывает Farm Aggregation Service, Billing и Core Business Logic.
- **Агент на ферме не меняется:** существующий MVP-агент (толстый клиент) становится клиентом SaaS-платформы без архитектурных изменений.

### C2 — Пример интеграции: АгроТех Х как клиент
**Диаграмма:** [C2_integration.puml](C2_integration.puml)

АгроТех Х подключается к платформе на тарифе **Enterprise**:
1. Агенты-ферм отправляют sync-данные через API Gateway по API-ключу.
2. SaaS Adapter аутентифицируется через Auth Service (Client Credentials) и запрашивает аналитику через Public API.
3. Webhook Service доставляет события `animal.death` и `herd.count.updated` в SaaS Adapter, который обновляет учёт поголовья в 1С:Агро.
4. Web-портал АгроТех Х обращается к Public API через Bearer-токен.

## Компромиссы и риски

| **Компромисс**                       | **Описание**                                                                                                       |
|:-------------------------------------|:-------------------------------------------------------------------------------------------------------------------|
| Вариант 2 vs Вариант 3 для всех      | Вариант 2 дешевле, но при strict-compliance клиентах (152-ФЗ) потребуется Вариант 3, что усложняет инфраструктуру. |
| Keycloak realm per tenant            | Гибкая изоляция, но при 100+ тенантах нужно мониторить производительность Keycloak.                                |
| Агент на ферме не меняется           | Упрощает переход, но Sync Service агента нужно обновить для передачи tenant_id в заголовке запроса.                |
